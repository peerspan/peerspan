# PeerFS local registration and host signing (PF-1)

Status: accepted local contract, merged in [#121](https://github.com/peerspan/peerspan/pull/121),
following the boundary plan in [#116](https://github.com/peerspan/peerspan/pull/116).
The first implementation slice is PF-1(a): preparation, lookup/list, release and
typed commit signing. Provider activation, fresh PeerFS host-backed initialization
and historical HostKeys remain subsequent PF-1 pieces. Remote read
authorization, object serving and cross-host pull remain PF-2/PF-3 in the
[delivery plan](peerfs-host-contract.md). No filesystem grant is created here.

Baseline: host `8701a2e982951d0be56693917f2650c84335e091` and PeerFS
[`6d65976`](https://github.com/peerspan/peerfs/tree/6d65976f69f901f9c126edb5d90256a9ac81bef6).
The local bridge composes PeerFS's existing `Signer` and `HostKeys` traits.
Both host implementations use this external contract; Rust is implemented here.

## 1. Scope and initialization order

The first implementation supports **new host-backed spaces**. Existing spaces
using `signing.key`, free-form host aliases or `hosts` remain unchanged; there
is no automatic conversion or rewriting of their signed history. A host-backed
space never loads, creates or falls back to either key file. An unexpected
`signing.key` or `hosts` file makes opening that mode fail.
Initial qualification is Linux, matching the installed host preview; macOS
socket-account verification and installation need their own platform gate.

PeerFS currently signs the initial commit inside `Space::init`, before its
server socket exists. Requiring a live provider before permitting any signature
would deadlock initialization. The selected order is:

1. The owner creates an empty private directory and explicitly prepares one
   host binding through the owner-local API. This authorizes typed local
   commit signing only. It is not a verified provider or remote registration.
2. PeerFS initializes that directory with the returned public binding and a
   host-backed signer **before** creating its first commit. The initial commit
   is host-signed; no temporary file key or unsigned initial branch is used.
3. The owner runs the local PeerFS server. Explicit activation verifies that
   server over its Unix socket before marking the binding registered.

Preparing, initializing and activating are separate recoverable operations.
The CLI must recover a retained binding after an unknown response; it must not
allocate another space or overwrite a partially initialized directory. Exact
human-facing CLI orchestration follows the local adapters; this contract adds
no promised one-command installation or guided sharing pane.

### Interrupted initialization

The new initializer holds the existing exclusive space lock. Before requesting
its initial signature it atomically writes/syncs mode 0600 `host-init.json`:

```text
{format:1,binding_id,message_base64}
```

`message_base64` is the exact bounded section 5 signing message for the initial
commit. Its tree must be the stored, verified empty tree, parents empty,
predecessor absent and message `Create the space`; host/key/binding must match
the immutable manifest. It fixes the chosen change ID, timestamp and optional
agent/session metadata across recovery. Write the signed object and initial
`main` reference durably before removing this receipt and syncing the directory.

An explicit initialization retry may resume that same well-formed receipt and
matching binding under the lock. Recover/store the exact deterministic signature
and compare-and-swap only an absent `main` or confirm that it already equals the
result. A different reference, unexpected workspace/branch, damaged receipt,
foreign binding or unsupported partial state is a conflict with no overwrite.
A fully initialized matching space reports its retained result without changing
any head, including one that moved since initialization. An old unreceipted
partial directory is not treated as an empty space.

Normal opening/serving refuses a pending initialization receipt; explicit
initialization recovery finishes it first. A failed initializer never removes
unrecognized files or replaces a directory to get a fresh inode. This receipt
contains no signing key or filesystem grant and is not a second database.

## 2. Names, paths and immutable binding

- `space_id`: `space_` followed by 32 lowercase hexadecimal digits, generated
  from 16 random bytes by the owner-local initiating client before dispatch.
  It names the logical space, not a path, agent, branch or permission.
- `binding_id`: `fsbind_` plus 32 lowercase hex digits, generated by the host
  once. It fences a particular local registration lifetime, not a credential.
- `network_id`, `context_id`: the existing exact DEC `net_`/`ctx_` identities.
  Both are pinned; a caller may not substitute a different descriptor under
  the same network ID. Root rotation within that context is not a replacement.
- `host_id`, `public_key`: the local host identity and canonical padded standard
  Base64 of its 32-byte Ed25519 public key. `host_id` is `host_` plus lowercase
  hexadecimal SHA-256 of those raw bytes. Labels are not accepted as host IDs.
- `directory`: absolute UTF-8 path, at most 4096 bytes, with no NUL, `.` or `..`
  components, repeated separators or trailing separator. The filesystem root
  itself is not a space. The directory and its ancestors must not be symlinks.
  It must belong to the daemon's effective UID and have mode 0700. Ancestors
  must be owned by that UID or root and not writable by other accounts; a
  root-owned sticky directory such as `/tmp` is allowed above the private root.
  The complete UTF-8 pathname after appending `/peerfs.sock` must fit 107 bytes,
  the supported Linux pathname-socket limit; reject longer paths at preparation.

Preparation opens/pins the directory without following symlinks and retains its
device/inode and account. It must be empty at first preparation. Exact replay
does not require continued emptiness. No process opens the PeerFS object store
or takes `space.lock` to validate a binding. Replacing the directory, changing
its ownership/privacy, redirecting an ancestor or using a second live binding
for the same directory is refused. Checks use the pinned directory rather than
trusting a caller-supplied path after validation.

Bindings have durable states `prepared`, `registered`, `released`. Registered
means activation once verified the selected provider; it does not assert that
it is running now. A released binding is a tombstone. Neither ID is reused.
The first version supports no path relocation, rebinding, context switch or
key replacement under an existing space ID. A restored/replaced directory
requires a later explicit recovery contract, not an implicit inode update.

The private registration view is exactly:

```text
{format:1,space_id,binding_id,network_id,context_id,host_id,public_key,
 directory,state,created_at}
```

`created_at` is immutable UTC RFC3339 with whole seconds. Local paths, UID,
inode information and registration views are never capability advertisements,
agent-tool results, peer responses or routine log fields.

## 3. Owner-local API

All routes below are on private `admin.sock` only. The authenticated peer,
pairing, helper, agent adapter and MCP routers return404 for these routes.
The administration boundary is the local account, as for other owner actions;
`binding_id` is not a bearer token and does not narrow that account's authority.

Every JSON object has exactly the stated fields. Reject duplicate/unknown
fields, null, wrong types, invalid UTF-8, trailing JSON and noncanonical binary
encodings. Unless specified, body limits are 8 KiB and each complete operation is
bounded to 5 seconds, including admission, local checks and database work.
The server must check cancellation/deadline before its atomic mutation; an
unknown response is recovered by exact lookup, not inferred to be a rollback.

| Operation | Exact request | Success |
| --- | --- | --- |
| `POST /v1/fs/spaces` | `{space_id,network_id,context_id,directory}` | 201 private view in `prepared`; exact replay 200 with the retained view |
| `GET /v1/fs/spaces` | No body/query | 200 array of nonreleased views sorted by `space_id`; at most 256 live bindings |
| `GET /v1/fs/spaces/{space_id}` | No body/query | 200 exact retained view, including a tombstone |
| `POST /v1/fs/spaces/{space_id}/activate` | `{binding_id}` | 200 `{registration:VIEW,provider:{state:"verified",observed_at}}` |
| `POST /v1/fs/spaces/{space_id}/release` | `{binding_id}` | 200 retained view in `released`; exact replay 200 |
| `POST /v1/fs/spaces/{space_id}/sign-commit` | `{binding_id,message_base64}` | 200 `{host_id,public_key,signature}`; section 5 |
| `POST /v1/fs/spaces/{space_id}/host-keys/check` | `{binding_id,host_id,public_key}` | 200 `{host_id,public_key,recognized}`; section6 |

Preparation requires a locally adopted, verified DEC context and the local
host's current admitted membership in it. It prepares no authority statement,
policy, invitation, project attachment or filesystem contents. Concurrent exact
requests create one binding; the same ID with changed terms or the same
directory with a different live ID returns 409. At the live-binding limit,
creation returns 429 without a row; exact replay/lookup/release remains usable.
An exact replay recovers its immutable prior outcome, including a tombstone,
before checking eligibility for new creation. It never reactivates a binding
or renews membership. Later signing/activation rechecks its own live guards.

List and exact lookup are pure local reads: no provider probes, network IO,
identity creation, state repair, signing, expiry refresh or implicit activation.
Release atomically disables local signing and every later resource operation
for this binding. It does not delete files/objects, stop a process, erase
historical signatures or recall bytes already delivered. Later filesystem
access decisions must require a live registered binding as well as their grant.

## 4. PeerFS provider identity and process lifetime

Fresh host-backed spaces use `peerfs space 3` as the first line of `FORMAT`.
Their immutable `host-binding.json` is durably written with mode 0600 before the
first commit. The manifest is exactly:

```text
{format:1,mode:"peerspan-host-v1",space_id,binding_id,network_id,context_id,
 host_id,public_key,host_socket}
```

`host_socket` is the explicitly selected absolute owner-local socket path,
not an environment default or network endpoint. It must fit the same 107-byte
Linux pathname bound, with no NUL or abstract address. This local configuration
is excluded from provider identity responses. Opening a host-backed space must
validate the manifest and exact host public identity over that socket before
using its signer. No hostname, `--host` alias, local key file, caller-selected
public key or changed host state may override it. Ordinary legacy mode retains
its existing API/behavior; mode detection is explicit, not a failed-RPC fallback.
Old PeerFS binaries must refuse space format 3 rather than open it without its
host signer. Legacy spaces keep format 2; changing only the FORMAT marker is not
a migration. Space format and immutable commit format are separate versions.
Choose that mode before opening or initializing the space: calling the legacy
constructor and replacing its signer afterward would load a forbidden file key
or sign the initial commit with it. In host-backed mode the legacy key-file
administration (`POST /v1/hosts` / `peerfs hosts add`) returns 409 and writes no
file; verification always uses the host adapter. Reading the legacy local
hosts file is not a source of trusted keys in this mode.

The new PeerFS `GET /v1/host-bridge` response is exactly:

```text
{format:1,protocol:"peerfs-host-v1",space_id,binding_id,network_id,context_id,
 host_id,public_key,directory}
```

This endpoint reads the loaded immutable binding and configured signer identity.
It needs neither the space mutex nor a host callback. A legacy file-key provider
returns 404. Keep `GET /v1/space` unchanged: its existing clients reject unknown
fields. A new endpoint avoids breaking those local clients.

Activation connects only to `peerfs.sock` inside the pinned private directory.
Require a real socket owned by the expected UID, mode 0600, Linux `SO_PEERCRED`
matching that UID, unchanged directory identity, and an exact identity-response
match. Reject a substituted process/account/socket, changed identity, extra
response fields or protocol mismatch. The response body is at most 8 KiB; connect
has a 1 second limit within the complete 5 second operation. Do not expose a socket
path supplied in an incoming peer request or follow provider redirects.

Activation snapshots the binding, performs IO with no host database mutex/
transaction held, rechecks the same binding and directory, then atomically sets
`registered`. A concurrent release or changed binding prevents that commit.
Exact activation on a registered binding probes again without another durable
transition. `observed_at` identifies this probe, is not retained, and makes no
promise about future availability. Timeout, refusal or malformed identity
leaves the prior registration state unchanged.

A stopped provider stays registered but unavailable. The host does not start,
restart or take the lock of another process. Socket recreation by the same
correct provider is allowed; directory/space replacement is not. Host restart
preserves prepared/registered/tombstoned bindings and validates their structure;
it does not probe a provider at startup or declare it ready from a stored row.
Fresh provider verification is required before any future remote use.

## 5. Typed commit signing

The signer endpoint accepts `prepared` or `registered` bindings. Thus fresh
initialization, local offline commits and commits while the provider holds its
space lock can work. It never calls PeerFS, a helper, another host, a person
signer or `ssh-agent`. It uses only the selected local host Ed25519 key.
Release, a changed directory/account/host key or an unavailable host fails;
there is no alternate key, newly generated identity or unsigned-commit fallback.

The request body is at most 96 KiB; decoded `message_base64` is at most65,536 bytes
and must use canonical padded standard Base64. The decoded bytes must equal:

```text
ASCII("peerfs 2026-10-27 commit signature") || 00 || UNSIGNED_COMMIT_V3
```

`UNSIGNED_COMMIT_V3` contains the following fields in exactly this order:

| Field | Canonical bytes and additional bridge limits |
| --- | --- |
| format | One byte 03 |
| tree | 33-byte object ID: algorithm byte 01 followed by a 32-byte digest |
| parent count / parents | Minimal unsigned LEB128 u64,0..64; that many 33-byte object IDs, in original order |
| change | LEB128 byte length 16, then16 bytes |
| author host | LEB128 byte length and UTF-8; exactly this binding's real `host_id` |
| author agent / session | Each: tag00 for absent, or01 then length-prefixed UTF-8, at most 256 bytes; no other tag |
| time | Minimal unsigned LEB128 u64, milliseconds since Unix epoch |
| message | Length-prefixed UTF-8, at most16,384 bytes |
| predecessor | Tag00, or01 followed by one33-byte object ID |
| signature | One byte 00: the unsigned slot, mandatory |

Reject truncated, overflowed, padded/nonminimal integer encodings, invalid IDs,
unknown formats/tags, signed input, invalid strings and all trailing bytes before
key use. Check lengths/counts against remaining bytes before allocating.
The decoder must consume/re-encode the entire value identically, preserving
parent order and optional-field presence. Empty agent/session strings remain
distinct from absent values. There is no branch lookup, object read or mutation.

The result is the canonical Base64 Ed25519 signature of the **exact complete
decoded message**, plus the pinned host identity/key. Verify the returned
signature strictly before PeerFS stores its signed commit. Construct the signed
commit with tag 01 and the length-prefixed 32-byte public key and 64-byte signature;
retain PeerFS's existing kind-separated object hashing. The signature is part
of the object identity; it is not appended to an unsigned object's old ID.

Important scope: commit format 3 has **no space, network or branch field**. The
registration selects who may invoke this local operation and which host key is
used; it does not cryptographically bind these bytes to a space or prove their
tree exists there. The same canonical commit may occur in multiple spaces.
Agent/session fields are caller assertions, not authenticated actor evidence;
timestamps are not trusted clocks. PF-2 must separately bind access to the exact
serving host, space, branch and authorized closure. Do not add an unsigned space
label to a signature and claim it gained those properties.

Signing performs no durable write/event/publication and establishes no remote
permission or acceptance. Exact retries return the same deterministic signature.
The implementation must serialize the final binding check/key use with release
so a release committed before that check prevents signing. It holds no database
transaction across filesystem/provider/network IO.

The checked-in [public vectors](vectors/peerfs-local-signing.json) fix two
complete unsigned/signature examples and refused mutations. Their seed is public
test material, never an identity to install on a real host. These bytes are
contract vectors, not evidence that either adapter has run.

## 6. HostKeys: identity history, not current access

The local adapter calls `host-keys/check` for the commit's exact author host and
signature key. Require the live prepared/registered binding and its pinned
network context. The check is read-only, bounded, offline and makes no provider
callback, network fetch, key import, catalog adoption or trust-on-first-use.

`recognized:true` requires both:

1. The canonical Ed25519 key hashes to that exact `host_id`.
2. It is the local host key, or the selected DEC context retains a previously
   verified signed host admission establishing that key. For remote history,
   verification uses that admission's retained authenticated descriptor, root
   chain and authorizing proof closure under the existing DEC historical rules.
   A transport pin, contact, directory advertisement, raw cached string or a
   self-consistent hash without an admission is insufficient.

Expiry, subsequent host removal or later root rotation does not change an
already established host/key identity. It must not make valid historical
commits unverifiable merely because their author is offline or no longer has
access. Recognition says nothing about whether that author currently belongs,
could access this branch when signing, or can issue work now. Current filesystem
authorization is always a separate check. Missing retained proof or a valid
different key returns `recognized:false`; malformed IDs/keys return400. Damaged
retained proof fails closed with409 instead of returning a false verified fact.
No authority is reconstructed from a commit's untrusted timestamp.

## 7. Storage, errors and implementation order

The host adds one durable binding collection, unique by `space_id`, `binding_id`
and live pinned directory. Persist the immutable view, device/inode/account and
state atomically in its private SQLite database. Tombstones survive restart.
Do not add a second database, signing-key file, background provider monitor,
per-signature audit table or signature-byte log. This document allocates no
schema number on its own: the original baseline used29 for runtime tasks.
The implementation allocation below follows actual main, including its later
conversations schema30. Check existing identity/authority/history, old-binary
refusal and full-state restore.

PF-1(a) is additive **schema31 over prior-main30** (which includes agent
descriptions). Its private storage is exactly:

```sql
CREATE TABLE peerfs_bindings (
 space_id TEXT PRIMARY KEY NOT NULL,
 binding_id TEXT NOT NULL UNIQUE,
 network_id TEXT NOT NULL,
 context_id TEXT NOT NULL,
 host_id TEXT NOT NULL,
 public_key TEXT NOT NULL,
 directory TEXT NOT NULL,
 state TEXT NOT NULL CHECK (state IN ('prepared','registered','released')),
 created_at TEXT NOT NULL,
 device BLOB NOT NULL CHECK (length(device) = 8),
 inode BLOB NOT NULL CHECK (length(inode) = 8),
 uid INTEGER NOT NULL CHECK (uid BETWEEN 0 AND 4294967295)
);
CREATE UNIQUE INDEX peerfs_live_directory ON peerfs_bindings(directory) WHERE state != 'released';
CREATE UNIQUE INDEX peerfs_live_inode ON peerfs_bindings(device,inode) WHERE state != 'released';
```

Device/inode blobs are unsigned64-bit big-endian values. `format:1` is implicit
in the schema; it is emitted in every registration view. Validate the exact
schema, indexes and stored row shapes on startup; a missing/malformed object at
schema31 is corruption, not a request to recreate it. A pre31 state containing
this reserved namespace is refused atomically. Identity/key fields must match
the actual host; no filesystem/provider probe occurs during startup validation.
Older schema30 binaries refuse31. Existing synthetic old-version fixtures omit
this newer table; real upgrade/restore evidence uses genuine old binaries and
complete private backups, without version rewriting.

Failures use the host's ordinary `{code,error}` envelope, with fixed messages
that do not echo paths, bytes, provider errors or object content:

| Status / code | Meaning |
| --- | --- |
| 400 `invalid` | Malformed body/identity/encoding or unsupported signing format |
| 403 `forbidden` | Wrong local author host or account; preparation lacks admitted context |
| 404 `not_found` | Unknown space or a route on a nonowner interface |
| 409 `conflict` | Changed/released binding, changed/private-directory failure, incompatible provider, or damaged retained proof |
| 413 `too_large` | Body/decoded-message bound exceeded |
| 429 `limit` | The 256-live-binding limit, no row committed |
| 503 `unavailable` | Provider/host signer unavailable or operation deadline exceeded |
| 500 `internal` | Other internal failure; no raw exception/OS/SQLite/provider text |

The 429 body additionally carries the ordinary `limit:"fs_spaces"` field.
`error` is exactly `invalid request`, `forbidden`, `not found`, `conflict`,
`too large`, `limit exceeded`, `unavailable` or `internal error` respectively.
Parent-count and individual string limits are400; the complete body and decoded
message limits are413. Required-key lookup before an unknown record returns 404;
an existing record with a mismatched `binding_id` returns 409. No lower-level
exception is logged by these operations.
For filesystem refusals, a newly proposed root owned by another UID is403;
a retained root whose ownership/privacy/inode changes is409. A bad new root's
mode, symlinked path or unsafe ancestor is409; a malformed pathname is400.
A later activation's socket-account mismatch is403. Requests with valid shapes
to an unknown space are404; malformed bodies on existing spaces are400.

Implement in reviewable pieces: (a) registration storage and typed host signing,
(b) fresh host-backed PeerFS initialization and immutable provider identity,
(c) activation/lifetime and historical HostKeys adapter. The first piece must
not be advertised as usable network replication. PF-2/PF-3 follow with their
own exact policy/closure contracts; Go consumes the same boundary contract.

## 8. Independent verification

After this contract is reviewed, a separate author writes one compact PF-1
black-box suite from it, reusing existing public fixtures. Keep it under 120s
and about 1,000 lines; report measured cost and place it in the appropriate tier
under [DEC-OWN14/15](conformance-budget-proposal.md). Do not duplicate whole
onboarding ceremonies for parser cases or manufacture product rows in SQLite.

Required checks, with per-operation 5s bounds and unchanged existing guards:

- Fresh empty root preparation, exact replay, conflicting ID/path/context,
  concurrent prepare, limit/release, pure read/list, and durable restart.
- Reject symlinked, replaced, public or wrong-account roots/sockets; prove no
  activation transition on refusal/timeout/concurrent release. A genuine
  host-backed provider activates; an old file-key server does not.
- Initialize one real fresh PeerFS space with host signing before its provider
  exists; verify its initial commit and public key. Verify no file key exists,
  no unsigned initial reference appears, and restart uses the same identity.
  The old PeerFS binary must refuse its new space format without mutation;
  unchanged legacy format 2 spaces still work under old and new binaries.
- Interrupt initialization before signing, after object storage and after the
  initial reference write. Resume the same receipt/change/time/head; no second
  initial identity or file key. Repeating init after ordinary work must not
  reset a branch. Corrupt/foreign receipts or divergent references refuse
  without deleting files or silently replacing a directory.
- Independently check the public vectors; against a genuine fixture host use
  equivalent messages with its discovered host ID and verify its actual
  signatures with its public key. Negative format/domain/author/length/LEB128/tag/
  trailing-byte mutations, exact maximum message/parent/body bounds and one
  over each. Repeated signing is deterministic and changes no durable rows,
  permissions, peer counters or original/person/device/root key files.
- Sign while the provider holds its space mutex; fixed provider identity needs
  no callback and neither process deadlocks. Kill the provider: local signing
  still works, activation refuses, registration persists. Kill the host: PeerFS
  refuses a new commit without moving the branch or creating a fallback key.
- Genuine historical remote admission yields true after ordinary expiry/removal
  and root rotation with retained proof. Unknown, wrong-context, wrong-key,
  contact-only and unverified aliases fail; lookup changes no authority/state.
- Release refuses subsequent signing; a release committed before the final
  signing check prevents success. All local bridge routes are absent on peer/adapter/pairing/helper
  interfaces. Registration and signatures confer no remote access.
- Upgrade/restore uses actual old/new binaries and private backups. Preserve
  ordinary identity, grants, guided state and conversations; do not rewrite
  `user_version` or edit rows to create an apparent upgrade or rollback.

These checks establish the local boundary only. Installed cross-host content,
closure/signature integrity, interruption/resume, same-person/cross-person
consent and managed-NAT/relay behavior remain later acceptance gates. No model
turn is needed for PF-1.

## Decisions and discarded options

- Selected: prepare local signing before live provider activation. Discarded:
  require a live socket before initialization, sign the first commit with a
  temporary key, or let a failed provider check create a registered space.
- Selected: new host-backed spaces and explicit mode. Discarded: silently
  convert alias/file-key history or fall back after a failed host callback.
- Selected: a separate provider-identity endpoint. Discarded: extend the strict
  legacy `SpaceInfo` object and break existing local clients.
- Selected: complete canonical commit3 validation and existing PeerFS signature
  bytes. Discarded: generic signing, prefix-only checks, invent a second commit
  codec on the wire, or claim a space ID absent from the signed bytes is bound.
- Selected: retained authenticated key identity independent of current access.
  Discarded: trust every self-consistent supplied host/key, trust contacts, or
  reject all historical authors when membership expires.
- Selected: no automatic relocation/rebinding in this first local slice.
  Discarded: follow replaced directories or silently switch providers under
  previously reviewed space identities. A later recovery contract handles it.
